# Level 2 — Authentication

**Goal:** people can create an account, sign in, stay signed in across page reloads, and sign out. Built the way production apps do it: a short-lived **access token** plus a rotating **refresh token** in an httpOnly cookie.

**What you can do at the end of Level 2:** open any page while signed out → you're sent to *Sign in* → create an account or sign in → you land where you were going → reload and you're still signed in → *Sign out* from the account menu → protected pages send you back to *Sign in*.

> Builds on [LEVEL_1.md](LEVEL_1.md) (error format, CORS, typed API client, app shell).

## 1. The design in one page

### Two tokens, two jobs

| | Access token | Refresh token |
|---|---|---|
| What | A signed JWT | 32 random bytes (base64url) |
| Lifetime | **15 minutes** | **7 days** |
| Sent as | `Authorization: Bearer <token>` header | Cookie `devpulse_refresh` |
| Stored in the browser | **JavaScript memory only** (a module variable) | **httpOnly cookie**: JavaScript can't read it |
| Stored on the server | Nowhere (self-contained, verified by signature) | **SHA-256 hash** in the `refresh_tokens` table |
| Used for | Every API call | Only `POST /api/auth/refresh` (cookie path `/api/auth`) |
| Revocation | Blacklisted in Redis on logout until it expires | Row marked `revoked_at` |

**Why two?** A JWT can be checked without a database lookup, which makes every request fast, but it can't easily be "un-issued", so it must be short-lived. The refresh token is the long-lived proof of a session; because the server stores it, it can be revoked at any time.

**Why memory + httpOnly cookie, not `localStorage`?** Anything in `localStorage` can be read by any script on the page, so a single XSS bug would leak the token. An httpOnly cookie is invisible to JavaScript. The access token in memory disappears on reload, which is fine: the app silently gets a new one from the cookie.

### The flows

```
REGISTER   POST /api/auth/register {name,email,password}
           → 201 {id,name,email,role}            (then the frontend signs in automatically)

LOGIN      POST /api/auth/login {email,password}
           → 200 {accessToken, tokenType, expiresIn: 900, user}
             Set-Cookie: devpulse_refresh=<R1>; HttpOnly; SameSite=Strict; Path=/api/auth; Max-Age=604800

API CALL   GET /api/auth/me   Authorization: Bearer <access>
           → 200 {id,name,email,role}

EXPIRED    GET /api/auth/me   (access token expired)        → 401 "Access token has expired"
           POST /api/auth/refresh   Cookie: R1               → 200 {new access…}  Set-Cookie: R2
           GET /api/auth/me   (retried with the new token)   → 200          ← the user never notices

RELOAD     (token lost from memory) POST /api/auth/refresh   Cookie: R2  → 200 + R3

LOGOUT     POST /api/auth/logout   Bearer <access>  Cookie: R3
           → 204  Set-Cookie: devpulse_refresh=; Max-Age=0
             (R3's whole family revoked in the DB, access token's id blacklisted in Redis)
```

### Rotation and reuse detection

Every refresh **replaces** the refresh token: R1 → R2 → R3. The old row gets `revoked_at` and `replaced_by_id`. All tokens that descend from one login share a `family_id`.

If a **revoked** token is ever presented again, someone kept a copy: either an attacker stole it, or the real user did, and they are now racing. The server can't tell which, so it **revokes the whole family**: both sides are signed out and the stolen token becomes useless.

One exception: two browser tabs refreshing at the same moment with the same cookie. The second one finds the token *just* rotated. Within **30 seconds** of a rotation this is treated as a harmless race: the request is rejected, but the family is kept and the cookie is left alone (the browser already holds the newer one). The frontend also prevents the race in the first place (section 4.2).

## 2. Database: `V3__refresh_tokens.sql`

```sql
CREATE TABLE refresh_tokens (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id        BIGINT       NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    token_hash     VARCHAR(64)  NOT NULL UNIQUE,
    family_id      UUID         NOT NULL,
    expires_at     TIMESTAMPTZ  NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    revoked_at     TIMESTAMPTZ,
    replaced_by_id BIGINT       REFERENCES refresh_tokens (id) ON DELETE SET NULL
);
-- indexes on user_id, family_id, expires_at
```

| Column | Purpose |
|---|---|
| `token_hash` | SHA-256 of the raw token as 64 hex characters. `UNIQUE` gives a fast exact lookup. The raw token is never stored, so a database leak doesn't leak usable sessions. |
| `family_id` | Groups the rotation chain from one login, so "revoke the family" is one `UPDATE`. |
| `revoked_at` | `NULL` = usable. Set on rotation, logout, or reuse detection. |
| `replaced_by_id` | Points at the token that replaced this one. Distinguishes "rotated" (has a replacement) from "logged out" (no replacement). |
| `ON DELETE CASCADE` | Deleting a user deletes their tokens. |
| `TIMESTAMPTZ` | Timestamp with time zone; maps to Java `Instant`. |
| Indexes | `user_id` (revoke all of a user's sessions), `family_id` (revoke a family), `expires_at` (cleanup job). |

Flyway runs this automatically on startup; Hibernate then **validates** that the entity matches (`ddl-auto=validate`).

## 3. Backend, class by class

### 3.1 Configuration

**`config/JwtProperties.java`** binds `jwt.*`:
- `secret`: the HMAC signing key (≥ 32 bytes).
- `accessTokenTtl` (`Duration`, default 15 min) and `refreshTokenTtl` (default 7 days). Spring converts `15m` / `7d` strings into `Duration` automatically.
- Replaces the old `expiration` (milliseconds, 24 h).

**`config/RefreshCookieProperties.java`**, a record bound to `auth.refresh-cookie.*`:

| Property | Value | Why |
|---|---|---|
| `name` | `devpulse_refresh` | |
| `secure` | `false` locally (`AUTH_COOKIE_SECURE`) | `Secure` cookies are only sent over HTTPS; localhost is http. Must be `true` once deployed. |
| `same-site` | `Strict` | The browser never sends the cookie on requests started from another site. This is the **CSRF protection**. |
| `path` | `/api/auth` | The cookie is only sent to auth endpoints, never to the rest of the API. |

**`config/TimeConfig.java`**
- `@Bean Clock clock()` → `Clock.systemUTC()`. Every class that needs "now" (token expiry) injects the `Clock` instead of calling `Instant.now()`, so unit tests can pass `Clock.fixed(...)` and test expiry without waiting.
- `@EnableScheduling` turns on `@Scheduled` methods (the cleanup job).

**`application.properties`**

```properties
jwt.access-token-ttl=${JWT_ACCESS_TOKEN_TTL:15m}
jwt.refresh-token-ttl=${JWT_REFRESH_TOKEN_TTL:7d}
auth.refresh-cookie.name=devpulse_refresh
auth.refresh-cookie.secure=${AUTH_COOKIE_SECURE:false}
auth.refresh-cookie.same-site=Strict
auth.refresh-cookie.path=/api/auth
```

### 3.2 Entity and repository

**`entity/RefreshToken.java`**: a JPA entity mapped to `refresh_tokens`. `@ManyToOne(fetch = LAZY)` to `User` (the user is only loaded when needed). Two helpers:
- `isRevoked()` → `revokedAt != null`
- `isExpiredAt(now)` → `!expiresAt.isAfter(now)` (expired at or after the expiry instant)

It doesn't extend `BaseEntity` because its timestamps are `Instant` and `created_at` is `NOT NULL`.

**`repository/RefreshTokenRepository.java`** (Spring Data JPA: the interface is implemented automatically)

| Method | Query | Used by |
|---|---|---|
| `findByTokenHash(hash)` | derived from the method name | logout |
| `findByTokenHashForUpdate(hash)` | `select t from RefreshToken t join fetch t.user where t.tokenHash = :tokenHash` with `@Lock(PESSIMISTIC_WRITE)` | rotation |
| `revokeFamily(familyId, now)` | `update … set revokedAt = :now where familyId = … and revokedAt is null` | logout, reuse detection |
| `revokeAllForUser(userId, now)` | same, per user | password change (Level 3) |
| `deleteExpiredBefore(cutoff)` | `delete … where expiresAt < :cutoff` | cleanup job |

- **`PESSIMISTIC_WRITE`** issues `SELECT … FOR UPDATE`: the row stays locked until the transaction ends, so two simultaneous refreshes with the same token run one after the other instead of both rotating it.
- **`join fetch t.user`** loads the user in the same query (it's needed right after).
- **`@Modifying`** marks the `update`/`delete` queries as writes; they return the number of rows affected.

**`repository/UserRepository.java`** gains `findByEmailIgnoreCase` and `existsByEmailIgnoreCase`, so `Ada@Example.com` and `ada@example.com` are the same account.

### 3.3 `security/JwtService.java`: issuing and checking access tokens

Constructor:
- `Keys.hmacShaKeyFor(secret bytes)` builds the HMAC-SHA key. It throws `WeakKeyException` **at startup** if the secret is shorter than 256 bits: fail fast rather than run with a guessable key.
- Builds one reusable `JwtParser` that verifies the signature, requires `iss = devpulse-ai`, and uses the injected `Clock` for expiry checks.

**`issue(User user)` → `IssuedAccessToken(value, expiresAt)`**

```java
Jwts.builder()
    .id(UUID.randomUUID().toString())          // jti: unique id, used for the logout blacklist
    .issuer("devpulse-ai")
    .subject(String.valueOf(user.getId()))     // who: the user id, not the email
    .claim("email", user.getEmail())
    .claim("role", user.getRole().name())
    .issuedAt(Date.from(now))
    .expiration(Date.from(now.plus(accessTokenTtl)))
    .signWith(key)                              // HS256
    .compact();
```

The subject is the **user id**, so tokens keep working when a user changes their email (Level 3). Before Level 2 it was the email.

**`parse(String token)` → `AccessTokenClaims(tokenId, userId, expiresAt)`**
- Success: reads `jti`, `sub` (parsed to `Long`), and `exp`.
- `ExpiredJwtException` → `InvalidTokenException("Access token has expired")`.
- Any other `JwtException` (bad signature, malformed, wrong issuer) or `IllegalArgumentException` (empty token, non-numeric subject from an old token) → `InvalidTokenException("Access token is invalid")`.

**`security/InvalidTokenException.java`** is a plain `RuntimeException` carrying the reason. The filter catches it; it never reaches a controller.

### 3.4 `service/RefreshTokenService` + `RefreshTokenServiceImpl`: the refresh-token lifecycle

Interface records:
- `IssuedRefreshToken(id, value, expiresAt)`: `value` is the raw token, handed to the client exactly once.
- `Rotation(user, refreshToken)`: the result of a successful refresh.

**`issue(User)`** → `create(user, UUID.randomUUID())`: a new family.

**`create(user, familyId)`** (private)
1. `SecureRandom.nextBytes(32 bytes)`, encoded as URL-safe base64 without padding (43 characters, safe in a cookie).
2. Saves a `RefreshToken` with `hash(raw)`, the family, `createdAt = now`, `expiresAt = now + 7 days`.
3. Returns the raw value together with the saved id.

**`hash(raw)`** (static): SHA-256 → 64 hex characters (`HexFormat`). A plain fast hash is fine here (no bcrypt, no salt) because the input is 256 random bits: there is nothing to guess or look up in a dictionary.

**`rotate(rawToken)`**: the heart of it.

```
find row by hash, locked              → none?            InvalidRefreshToken("Refresh token is invalid")
if revoked:
    rotated < 30 s ago (has replacement)? → reject, KEEP family, don't clear cookie
    otherwise (stolen / logged out)       → revoke whole family, log a warning, reject
if expired                            → InvalidRefreshToken("Session has expired, please sign in again")
create next token in the same family
mark current: revokedAt = now, replacedById = next.id
return Rotation(user, next)
```

- `@Transactional(noRollbackFor = InvalidRefreshTokenException.class)`: normally a runtime exception rolls the transaction back, which would **undo the family revocation**. `noRollbackFor` keeps that update even though the request fails.
- The 30-second window is `CONCURRENT_REFRESH_GRACE`.

**`revokeFamily(rawToken)`**: logout. Looks the token up and revokes its family; unknown tokens are silently ignored (logout must never fail).

**`revokeAll(userId)`**: every session of a user (for Level 3's password change).

**`deleteExpiredTokens()`**: `@Scheduled(cron = "0 0 3 * * *")`, daily at 03:00. Deletes expired rows, which are useless, to keep the table small.

### 3.5 `service/AuthService` + `AuthServiceImpl`: the use cases

`AuthResult(response, refreshToken)` carries the JSON body plus the refresh token the controller turns into a cookie (the service doesn't know about HTTP).

**Constructor:** computes `dummyPasswordHash = passwordEncoder.encode("not-a-real-password")` once.

**`register(RegisterRequest)` → `UserResponse`**
1. `normalizeEmail`: trim + lowercase (`Locale.ROOT`, so it's not affected by the server's language settings).
2. `existsByEmailIgnoreCase` → `EmailAlreadyExistsException` (→ 409).
3. Builds the `User` (trimmed name, `ROLE_USER`, **bcrypt** hash of the password).
4. `saveAndFlush` inside `try`: if two sign-ups with the same email race past the check, the database's unique constraint throws `DataIntegrityViolationException`, which is turned into the same 409.

**`login(LoginRequest)` → `AuthResult`**
1. Finds the user case-insensitively (or `null`).
2. **Always** runs `passwordEncoder.matches(...)`: against the real hash, or against `dummyPasswordHash` if the email doesn't exist. bcrypt deliberately takes ~100 ms; skipping it for unknown emails would make them answer faster and let an attacker discover which emails are registered (a **timing attack**).
3. Same error for both failures: "Invalid email or password".
4. Success → `refreshTokenService.issue(user)` + `issueTokens(...)`.

**`refresh(rawRefreshToken)`**: no cookie → `InvalidRefreshTokenException("Not signed in")`; otherwise `rotate(...)` + `issueTokens(...)`.

**`logout(rawRefreshToken, accessToken)`**: both optional.
- Refresh token → `revokeFamily`.
- Access token → `parse` it; if still valid, `jwtBlacklistService.blacklist(jti, remaining lifetime)`. The Redis key expires exactly when the token would have, so the blacklist cleans itself up. An already-invalid token is ignored.

**`currentUser(userId)`** → `UserResponse`, or 404.

**`issueTokens(user, refreshToken)`** (private): `jwtService.issue(user)` → `AuthResponse(accessToken, "Bearer", ttl in seconds, UserResponse.from(user))`.

### 3.9 `security/JwtAuthenticationFilter.java`: reading the token on every request

A `OncePerRequestFilter` (runs exactly once per request), placed before Spring's username/password filter.

```
no "Authorization: Bearer …" header         → continue, anonymous
parse(token) throws InvalidTokenException   → remember reason, continue anonymous
token id in the Redis blacklist             → reason "Session has ended, please sign in again"
user id no longer in the database           → reason "Account no longer exists"
otherwise                                   → load principal by id, put an Authentication
                                              into the SecurityContext
```

**Key design: the filter never rejects a request itself.** It only decides who you are. Spring Security's authorization rules decide whether that's enough: public endpoints still work with a broken token, and protected ones end up in `JsonSecurityErrorHandler.commence`, which reads the stored reason (`AUTH_ERROR_ATTRIBUTE`) and answers **401 with that message**. Previously a bad token threw inside the filter and became a **500**.

`WebAuthenticationDetailsSource` attaches the client IP and session details to the authentication (useful in logs and audits).

**`security/CustomUserDetailsService.java`**: added `loadUserById(id)`, since tokens now carry the id. Both lookup methods share `toPrincipal(User)`. `loadUserByUsername` is now case-insensitive.

### 3.10 `config/SecurityConfig.java`: Level 2 changes

- Public endpoints narrowed from `/api/auth/**` to exactly `POST` register / login / refresh / logout, so `/api/auth/me` requires a token.
- `sessionCreationPolicy(STATELESS)`: Spring never creates an HTTP session; every request carries its own token.
- CSRF stays disabled, with the reason in a comment: authentication is a header (browsers never attach it automatically) and the only cookie is `SameSite=Strict` and limited to `/api/auth`.

### 3.11 Errors

- **`exception/InvalidRefreshTokenException.java`** → 401. Carries `clearCookie` (default `true`). It's `false` only for the concurrent-refresh case, so that 401 doesn't delete the newer cookie the other tab just received.
- **`GlobalExceptionHandler.handleInvalidRefreshToken`** adds the clearing `Set-Cookie` to the 401 when `shouldClearCookie()`, so a dead cookie is removed from the browser.
- **`JsonSecurityErrorHandler.commence`** uses the filter's reason as the 401 message.

### 3.12 Other changes

- `UserService`/`UserServiceImpl`: `register` and `login` moved out to `AuthService`; the class now only handles profile operations (cleaned up in Level 3).
- `.env.example`: `JWT_EXPIRATION` replaced by optional `JWT_ACCESS_TOKEN_TTL`, `JWT_REFRESH_TOKEN_TTL`, `AUTH_COOKIE_SECURE`.

## 4. Frontend, file by file

### 4.1 `lib/api/config.ts`
`API_BASE_URL` from `VITE_API_BASE_URL` (default `http://localhost:8080`). In its own module so `session.ts` and `client.ts` can both import it without a circular import.

### 4.2 `features/auth/session.ts`: the token and the refresh logic

| Export | What it does |
|---|---|
| `getAccessToken()` / `setAccessToken(t)` | Read and write the module-level `accessToken` variable: the only place the token lives. |
| `onSessionEnded(listener)` | Subscribe to "the session died mid-use"; returns an unsubscribe function. |
| `notifySessionEnded()` | Clears the token and calls every listener. |
| `refreshSession()` | Trades the cookie for a new access token: returns the `AuthResponse`, or `null` if there's no valid session. |

**`refreshSession` is single-flight:**

```ts
let refreshInFlight: Promise<AuthResponse | null> | null = null
export function refreshSession() {
  refreshInFlight ??= withCrossTabLock(requestRefresh).finally(() => { refreshInFlight = null })
  return refreshInFlight
}
```

`??=` assigns only if nothing is in flight. Everyone who asks for a refresh while one is running gets **the same promise**: React StrictMode's double effect, three API calls failing with 401 at once… all share one request. That's essential, because the backend rotates the token: two parallel refreshes with the same cookie would look like token reuse.

**`withCrossTabLock(task)`**: other tabs share the cookie but not this module's memory. `navigator.locks.request('devpulse-auth-refresh', task)` (the **Web Locks API**) lets only one tab at a time run the refresh; the next tab waits, then refreshes with the cookie the first tab just received. Browsers without it (and jsdom in tests) fall back to running the task directly.

**`requestRefresh()`**: `fetch(POST /api/auth/refresh, { credentials: 'include' })`. `credentials: 'include'` is what makes the browser send and accept the cookie cross-origin (it pairs with the backend's `allowCredentials(true)`). On success it stores the token; on any failure (401, or the backend being down) it returns `null`, so the app shows *Sign in* instead of crashing.

### 4.3 `lib/api/client.ts`: the auth-aware fetch

`createClient<paths>({ baseUrl, fetch: authFetch, credentials: 'include' })`: every typed API call now goes through **`authFetch(request)`**:

```
retry = request.clone()                  // a Request body can only be read once
send with "Authorization: Bearer <token>"
if not 401, or we had no token, or it's an auth endpoint → return response
token = null; refreshed = await refreshSession()
refresh failed → notifySessionEnded(); return the 401
refresh ok     → send `retry` with the new token
```

- **Why `clone()`:** a POST body is a stream; after the first send it's consumed, so the retry needs a copy made in advance.
- **Why skip auth endpoints:** a 401 from `/login` means "wrong password", not "token expired"; retrying it through a refresh would be wrong (and `/refresh` itself would loop).
- **Why skip when there was no token:** then the 401 isn't an expiry, there's nothing to refresh.
- Uses `globalThis.fetch` at call time, so MSW in tests can intercept it.

### 4.4 `lib/api/errors.ts`

- **`ApiRequestError`**: an `Error` with `status` and the parsed `ErrorResponse` `body`. The getter `fieldErrors` turns `body.errors[]` into `{ email: 'Invalid email format', … }`.
- **`unwrap(result)`**: openapi-fetch returns `{ data, error, response }` instead of throwing. `unwrap` returns `data`, or throws `ApiRequestError`, so callers use normal `try/catch` (and TanStack Query sees failures as errors).
- **`errorMessage(error)`**: one place that turns anything into a user-facing sentence. A `TypeError` from `fetch` means the network failed → "Can't reach the server. Is the backend running?"

### 4.6 `features/auth/authContext.ts`

```ts
type AuthState =
  | { status: 'loading' }
  | { status: 'authenticated'; user: User }
  | { status: 'anonymous' }
```

A **discriminated union**: TypeScript only lets you read `user` after checking `status === 'authenticated'`, which makes "used the user while signed out" impossible to compile. The context adds `login`, `register` and `logout`. `useAuth()` throws outside the provider; `useCurrentUser()` returns the user and throws if called while signed out (only use it inside `RequireAuth` routes).

### 4.7 `features/auth/AuthProvider.tsx`

- **Start-up effect:** `refreshSession()` → `authenticated` with the returned user, or `anonymous`. The `cancelled` flag ignores the result if the component unmounted (StrictMode mounts, unmounts and remounts once in development).
- **Session-ended effect:** subscribes with `onSessionEnded`. When it fires: `queryClient.clear()` (drop the previous user's cached data), set `anonymous`, show the toast "Your session has ended. Please sign in again." The effect's return value unsubscribes.
- **`login(body)`** → `authApi.login` → `authenticated`.
- **`register(body)`** → `authApi.register`, then `login` with the same email and password (sign-up flows straight into the app).
- **`logout()`** → `authApi.logout`, clear the cache, `anonymous`.
- `useCallback` / `useMemo` keep the functions and the context value stable, so consumers don't re-render needlessly.

Mounted in `AppProviders` around the router (it uses TanStack Query and toasts, so it sits inside those providers).

### 4.8 `features/auth/routeGuards.tsx`

Both guards are **layout routes**: they render `<Outlet />` (the child route) or redirect.

- **`RequireAuth`:** `loading` → full-page spinner (`role="status"` plus visually hidden "Loading…" text); `anonymous` → `<Navigate to="/login" replace state={{ from: location }} />`; otherwise → `<Outlet />`.
- **`GuestOnly`** (login/register): `authenticated` → redirect to `state.from` (the page originally requested) or `/dashboard`; otherwise → `<Outlet />`.

This is how *open /repositories → sign in → land on /repositories* works: `RequireAuth` stores where you were going in the navigation **state**; after login, `AuthProvider` flips to `authenticated`, `GuestOnly` re-renders and redirects there. The login page itself never navigates.

### 4.10 `features/auth/schemas.ts`: validation with zod

```ts
loginSchema    = { email: trimmed, required, valid email;  password: required }
registerSchema = { name: trimmed 1–100; email: trimmed ≤ 255 valid;
                   password 8–72; confirmPassword }
                 .refine(password === confirmPassword, path: ['confirmPassword'])
```

- Mirrors `RegisterRequest.java` / `LoginRequest.java`, so most mistakes are caught instantly without a request. The backend still validates everything (never trust the client).
- `.pipe(z.email(...))` runs the email check only after trimming and the "required" check, so an empty field shows "Email is required", not "Enter a valid email".
- `.refine` is a cross-field rule; `path` attaches its error to the confirm field.
- `z.infer<typeof schema>` derives the TypeScript form types from the schema: one source of truth.

## 5. Security decisions, summarised

| Threat | Defence |
|---|---|
| XSS stealing tokens | Access token only in memory; refresh token in an **httpOnly** cookie |
| CSRF (another site triggering requests with your cookie) | `SameSite=Strict`; the cookie is scoped to `/api/auth`; the API itself authenticates by header, which browsers never attach automatically |
| A stolen refresh token | Rotation on every use + **reuse detection** revokes the whole family |
| A database leak | Refresh tokens stored as SHA-256 hashes; passwords as bcrypt hashes |
| Using a token after logout | The access token's `jti` is blacklisted in Redis until it expires; the refresh family is revoked |
| Guessing which emails exist | The same error and the same bcrypt work for unknown emails and wrong passwords |
| Forged or tampered JWT | HMAC-SHA256 signature + issuer check; secret ≥ 256 bits enforced at startup |
| Silent password truncation | 72-character limit matches bcrypt's 72-byte input |
| Crashes on bad input | Every bad token → JSON 401 with a reason; the filter never throws |

## 6. Explain it in an interview

**Walk me through your authentication.**
Email/password login returns a 15-minute JWT access token in the body and sets a 7-day refresh token as an httpOnly, SameSite=Strict cookie scoped to the auth endpoints. The frontend keeps the access token in memory and sends it as a Bearer header. When it expires, the client calls `/refresh`, which rotates the refresh token and returns a new access token; the original request is retried transparently.

**Why not just a long-lived JWT in localStorage?**
localStorage is readable by any script, so one XSS bug steals the session, and a JWT can't be revoked before it expires. Short-lived JWTs limit the damage; the revocable refresh token in an httpOnly cookie keeps the session.

**What is refresh-token rotation and reuse detection?**
Each refresh issues a new token and revokes the old one. All tokens from one login share a family id. If a revoked token shows up again, someone has a copy, so the whole family is revoked. There's a short grace window for two tabs refreshing at the same moment, and the client serializes refreshes with a single-flight promise and the Web Locks API.

**How does logout work with stateless JWTs?**
The refresh family is revoked in Postgres, and the access token's `jti` goes into Redis with a TTL equal to its remaining lifetime; the JWT filter checks that blacklist. The blacklist never grows beyond 15 minutes of tokens.

**Why hash refresh tokens with SHA-256 but passwords with bcrypt?**
Passwords are low-entropy and guessable, so they need a slow, salted hash. Refresh tokens are 256 random bits; there's nothing to guess, so a fast hash is enough and keeps lookups quick.

**How do you stop user enumeration on login?**
Identical error messages, and an unknown email still runs a bcrypt comparison against a dummy hash, so the response time is the same.

**Why does the JWT filter not reject requests?**
Separation of concerns: the filter only establishes identity; authorization rules decide access. Public endpoints keep working with a broken token, protected ones return a JSON 401 with the reason the filter recorded, and nothing becomes a 500.

**How do you test it?**
Unit tests with Mockito and a fixed `Clock` for expiry and rotation edge cases; full-stack integration tests over HTTP with Testcontainers (Postgres + Redis) covering cookies, rotation, logout and every bad-token case; frontend tests against an MSW fake that exercise the real retry-after-refresh logic, including concurrent 401s sharing one refresh.
